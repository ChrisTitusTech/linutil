# Linutil docs

Source for [linutil.christitus.com](https://linutil.christitus.com). It's a
plain Hugo site with no theme module: the layouts, CSS and JavaScript all live
in this directory. The look follows the Linutil TUI, using its default palette,
its rounded panels and its `[D]`/`[*]` rows.

## Running it locally

You need [Hugo](https://gohugo.io/installation/) 0.170 or newer. The standard
edition is enough; nothing here uses Sass.

```sh
hugo server --source docs
```

Run it from a full checkout of the repository. The homepage reads the script
catalog from `../core/tabs`, so the build fails if `docs/` is copied on its own.

To check a production build, build it somewhere outside the repository:

```sh
hugo build --source docs --destination /tmp/linutil-docs
```

## Layout

| Path | What's in it |
|------|--------------|
| `hugo.toml` | Site config: the header and sidebar menus, social links, mounts and outputs. |
| `content/` | The pages. `userguide/walkthrough.md` is generated by `cargo xtask docgen`, so don't edit it by hand. |
| `layouts/home.html` | The homepage. |
| `layouts/home.json` | The search index, published as `/index.json`. |
| `layouts/single.html`, `list.html` | Docs pages. Both use `_partials/docs-page.html`. |
| `layouts/404.html` | The not found page. |
| `layouts/_partials/` | Header, sidebar, footer, search dialog, status bar and the smaller pieces they use. |
| `layouts/_markup/` | Render hooks for headings, code blocks and alerts. |
| `layouts/_shortcodes/` | Shortcodes for use in content. |
| `assets/css/` | `main.css` for every page, `landing.css` for the homepage and 404. |
| `assets/js/` | `site.js` for menus, search, shortcuts and copy buttons. `landing.js` for the homepage menu. |
| `assets/icons/` | SVG icons, inlined with `partial "icon.html" "name"`. |
| `static/` | Favicons, fonts and their licences, and `CNAME`. |

## How it fits together

**Sidebar.** Built from `[[menu.sidebar]]` in `hugo.toml`. An entry that points
at a section (like `/userguide`) lists every page in it, ordered by `weight`.
An entry with children (like Help) lists those. The previous and next links at
the bottom of each page follow the same order.

**Header.** The dropdowns come from `[[menu.main]]`.

**Search.** `layouts/home.json` writes one entry for each `##` and `###`
section of every page. `site.js` downloads it the first time someone opens
search with `/` or Ctrl K.

**Homepage menu.** The browsable menu, the category panels and the script count
are built from `core/tabs`, which `hugo.toml` mounts as `data/tabs`. The Flags
panel is copied from `tui/src/dashboard.rs` into the front matter of
`content/_index.md`, so update it there when the TUI's flags change. Quick Help
lists the keys the preview itself answers to.

**Keyboard.** `/` opens search, and `p` and `n` go to the previous and next
docs page. On the homepage the menu takes the arrow keys, `j`/`k`, Enter, Esc
and `1`-`5` while it has focus.

## Writing pages

A page needs a `title`. Add a `weight` to place it in the sidebar, and
`toc: false` to hide the table of contents.

```md
---
title: Updating Linutil
weight: 5
---
```

New pages in `userguide/` or `dev/` show up in the sidebar on their own.
Fenced code blocks get a frame and a copy button. Alerts use GitHub's syntax:

```md
> [!NOTE]
> The dev branch may contain untested features.
```

`NOTE`, `TIP`, `IMPORTANT`, `WARNING` and `CAUTION` are supported.

## Deploying

`.github/workflows/docs.yaml` builds and publishes the site to GitHub Pages on
every push to `main` that touches `docs/`. The Hugo version is pinned there.

The live site shows the catalog of the latest release, which is what the
installer downloads, not `main`. The build checks out `core/tabs` from that
release and runs `cargo xtask docgen` before Hugo, so the homepage menu and the
walkthrough both match it. When a release is published, or a pre-release is
promoted, the same workflow opens a `docs-update` PR with the regenerated
walkthrough, which `auto-merge-docs.yaml` merges, and redeploys the site.

## What stays in sync

These update on their own a few minutes after a release goes live, meaning it's
published, or promoted from a pre-release, which is what the installer
downloads:

- the homepage menu, the category panels and the script count
- the walkthrough

A new pre-release on its own doesn't change the site. Any deploy between
releases also builds these from the latest release, so scripts merged to `main`
but not released yet never show up early.

These need a person:

- The hand-written pages, such as Getting Started, the FAQ and Automation. They
  go live from `main` as soon as they merge, so update them in the same change
  as the behavior they describe, including command-line flags, shortcuts and
  config options.
- The homepage Flags panel, copied from `tui/src/dashboard.rs` into
  `content/_index.md`.

The `docs-update` PR needs an `AUTO_MERGE` secret in the repository. Without
it the site still updates on release, but the walkthrough file in the
repository falls behind until someone runs `cargo xtask docgen`.
